一、场景背景

多智能体系统正从实验室走向生产。一旦给一群智能体授予工具与共享资源，问题就从"单个模型会不会乱说"升级为"**一群智能体会不会合谋、逃逸、耗尽资源**"——而这在上線前几乎无法系统性检验。

二、真实痛点（三条）

  • 逃逸风险无法预检：智能体被授予工具权限后，文件/网络/进程等逃逸路径难以穷举验证。
  • 禁止清单式沙箱易绕过：靠"不许调用 X"实现的隔离，总会有遗漏，且无法证明已穷尽。
  • 群体行为缺实验环境：合谋、资源耗尽等现象缺少可复现、可量化的观测平台。
目标用户：需要在上线前评估多智能体系统安全性的企业与超级个体；AI 对齐研究者。

三、SwarmBox 的根本做法

它不解释执行智能体的输出，而是把输出当作纯数据来解析。

因此文件、网络、进程、import、反射这些逃逸手段根本不在语法里——不是被禁止，而是无从调用。

提案 → 结构校验 → 身份校验 → 状态校验 → 闸门汇总 → 只追加账本　｜　不可逃逸是可审计的，而非需被信任的

为何"不可逃逸"可审计

每一次被拒提案都写入只追加账本，事后可完整回放：谁、在第几轮、试图做什么、命中哪条规则。安全性质不是声称的，是可核对的。

核心亮点：逃逸手段不在语法里

差异化创新点 · 对应评分维度「专业贴合与创新 25 分」

亮点 1 · 不解释执行，只作数据解析

常见沙箱的做法是"执行智能体输出，但禁止其中某些操作"——本质是黑名单，永远有遗漏。SwarmBox 反过来：智能体的输出被当作纯数据结构解析与校验，从不作为代码执行。因此文件、网络、进程、import、反射这些逃逸手段根本不在语法里。 这不是"禁止得更严"，而是"攻击面不存在"。

亮点 2 · 三重校验层层收窄

  • check_shape：提案形态是否合法（结构层）
  • check_identity：是否为该智能体本人（身份层）
  • check_state：当前世界状态下是否允许（状态层）

任一不过即由 screen() 拒绝并记账，不进入世界状态。

亮点 3 · 可审计而非需信任

只追加账本使"从未发生逃逸"成为可核对的历史记录，而不是一句承诺。

亮点 4 · 群体行为可量化

  • 5–20 个智能体共享公共资源池，多轮交互
  • 可观测协作 / 合谋 / 资源耗尽三种群体形态
  • collapse_rate、gini、collusion corr 等指标量化群体状态
  • compare() 支持对照实验，便于做消融研究

亮点 5 · 零依赖 + 完全离线可复现

  • 纯 Python 标准库，pip install 无内容，零网络访问
  • Python 3.9+，`git clone && python eval.py` 一次跑通 235 条断言
  • 附 REPORT.pdf 与 eval_chain.py 链式实验

落地价值

可直接作为企业多智能体系统上线前的安全评估基线；也可作为 AI 对齐研究中"合谋与资源耗尽"现象的标准实验环境。
